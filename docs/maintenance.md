# Регламент підтримки документації (Documentation Maintenance Regime)

**Проєкт:** RunTracker  
**Статус:** Дійсний (Active)  
**Редакція:** 1.0  
**Дата затвердження:** 2026-11-15  
**Політика супроводу:** Documentation as Code Lifecycle  

---

## 1. Головне правило супроводу: «Зміна коду = зміна документації»

> **ФУНДАМЕНТАЛЬНЕ ПРАВИЛО:**  
> **Жоден Pull Request або злиття (merge) до гілки `main` не приймається без одночасного оновлення зачепленої документації.**  
> Якщо комбінована зміна поведінки, сигнатури API, структури моделей даних або топології розгортання не супроводжується правками у відповідних документах паспорта, такий коміт вважається **дефектним** і блокується на етапі рев'ю (Documentation Debt Barrier).

### Інженерні засади регламенту:
1. Застаріла документація несе більшу загрозу, ніж відсутня, оскільки породжує когнітивне спотворення — хибну впевненість інженера у неактуальних контрактах системи.
2. Будь-який новий ендпоінт повинен бути зафіксований у [sdd.md](sdd.md) (таблиця API-контрактів та C4-діаграма) та [README.md](README.md).
3. Будь-яка зміна змінних середовища чи вимог до інфраструктури відображається в [isd.md](isd.md).
4. Архітектурні корекції принципового характеру фіксуються новими записами в [docs/architecture/adr/](architecture/adr/README.md) зі статусом `Accepted`, а застарілі маркуються як `Superseded`.

## 3. Процедура контролю деградації (Decay Prevention Workflow)
1. **Пре-коміт верифікація:** автор коду перевіряє співвідношення змінених файлів логіки та документації.
2. **Pull Request Quality Checklist:** обов'язковий пункт у PR template:
   - [ ] Додано/змінено API ендпоінти -> оновлено `README.md` та `docs/sdd.md`.
   - [ ] Змінено конфігурацію/порти/БД -> оновлено `docs/isd.md`.
   - [ ] Змінено концептуальні рішення -> додано новий ADR.
3. **Автоматизований моніторинг:** періодичний аудит Git CLI (`git log -1 --format=%cs`) для виявлення документів зі строком неактивності > 90 днів.
