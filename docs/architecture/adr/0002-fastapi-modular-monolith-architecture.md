# ADR 0002: Модульна монолітна архітектура на базі фреймворку FastAPI

- **Номер рішення:** ADR-0002
- **Дата ухвалення:** 2026-09-13
- **Статус:** Прийнято (Accepted)
- **Автор:** System Architect / Tech Lead
- **Сфера застосування:** Backend Architecture, API Tier

---

## 1. Контекст та постановка проблеми (Context)

Для системи RunTracker необхідно обрати архітектурний стиль побудови бекенду та веб-фреймворк. Вимоги:
1. Висока продуктивність обробки HTTP-запитів та асинхронні можливості.
2. Автоматична генерація контрактів API (OpenAPI 3.0 / Swagger) для ефективної взаємодії розробників та QA.
3. Простота супроводу та тестування: кодова база на початковому етапі має розмір ~1100–3000 рядків, команда невелика (1–3 інженери).
4. Чітке розділення відповідальності між маршрутизацією (HTTP), валідацією моделей, бізнес-логікою та персистентністю.

---

## 2. Розглянуті альтернативи (Alternatives Considered)

### Альтернатива 1: Мікросервісна архітектура (Distributed Microservices)
- *Опис:* Розподіл системи на 4 окремі сервіси: Runner Service, Workout Service, Gear Service, Plan Service з міжсервісною взаємодією через REST або брокер повідомлень (RabbitMQ).
- *Переваги:* Незалежне розгортання та масштабування окремих компонентів.
- *Недоліки:* Величезний інфраструктурний оверхед, складність оркестрації (Docker Compose / Kubernetes), мережеві затримки, складність забезпечення розподілених транзакцій та надмірний Bus Factor для невеликої команди.

### Альтернатива 2: Моноліт на базі Django (Django Web Framework)
- *Опис:* Використання класичного «batteries-included» фреймворку Django з Django REST Framework.
- *Переваги:* Вбудована адмін-панель, ORM, система автентифікації.
- *Недоліки:* Синхронна природа (вищий оверхед пам'яті), надмірна громіздкість для легковагого API, відсутність нативної сучасної підтримки типізації Python 3.12 і валідації Pydantic V2 «з коробки».

### Альтернатива 3: Модульний моноліт на базі FastAPI (Обрано)
- *Опис:* Єдиний розгортальний артефакт, структурований за чіткими функціональними доменами (`routers`, `services`, `models`, `schemas`, `privacy`), що працює на ASGI-сервері Uvicorn.
- *Переваги:* Нативна типізація Pydantic V2, автоматична генерація документації Swagger UI, низький footprint пам'яті, надзвичайна швидкість виконання запитів, прозоре тестування через `TestClient`.
- *Недоліки:* Спільний простір пам'яті вимагає суворої дисципліни архітектури для запобігання появі God Object та циклічних імпортів.

---

## 3. Прийняте рішення (Decision)

Ухвалити **Альтернативу 3**: побудувати бекенд RunTracker як **модульний моноліт на базі FastAPI (Python 3.12)**:
- Каталог `app/routers/` відповідає за обробку HTTP-запитів, статус-коди та серіалізацію.
- Каталог `app/services/` містить чисту бізнес-логіку (формули Карвонена, Рігеля, калькулятор зносу взуття, аналітика) без прямої прив'язки до HTTP-контексту.
- Каталог `app/privacy/` інкапсулює вимоги безпеки, маскування та санітизації даних.
- Заборонено прямий крос-імпорт між доменними сервісами з високим зв'язуванням (high coupling); взаємодія організовується через контракти або композицію.

---

## 4. Наслідки (Consequences)

### Позитивні наслідки:
- **Швидкість розробки та онбордингу:** один репозиторій, один процес розгортання, миттєве розуміння карти кодової бази.
- **Вбудована інтерактивна документація:** актуальний Swagger UI завжди доступний за посиланням `/docs`.
- **Безшовна підготовка до мікросервісів:** оскільки домени розділені на рівні модулів (`services/gear.py`, `services/plans.py`), за потреби будь-який модуль може бути винесений в окремий сервіс без переписування внутрішньої бізнес-логіки.

### Негативні наслідки та ризики:
- Необхідність суворого аудиту зв'язності (Coupling) та цикломатичної складності (контролюється за допомогою інструменту Radon та метрик Лекції 8).
- Усі компоненти ділять спільні ресурси процесора та пам'яті хоста.
