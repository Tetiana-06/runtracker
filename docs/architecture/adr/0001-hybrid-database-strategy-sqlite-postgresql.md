# ADR 0001: Гібридна стратегія збереження даних (SQLite для Dev/Test та PostgreSQL для Production)

- **Номер рішення:** ADR-0001
- **Дата ухвалення:** 2026-09-13
- **Статус:** Прийнято (Accepted)
- **Автор:** System Architect / Tech Lead
- **Сфера застосування:** Persistence Layer, Data Tier

---

## 1. Контекст та постановка проблеми (Context)

Система RunTracker розробляється як навчально-промисловий вебзастосунок. Ключовими вимогами до сховища даних є:
1. **Низький поріг входження для онбордингу нових інженерів:** можливість миттєвого локального запуску, налагодження та прогону тестів без попередньої установки, налаштування та адміністрування важких серверних СУБД (наприклад, PostgreSQL).
2. **Надійність і масштабованість у багатокористувацькому режимі (Production):** підтримка паралельних транзакцій, блокування на рівні рядків, збереження цілісності при високому навантаженні на запис.
3. **Швидкість CI/CD конвеєра:** виконання набору юніт-тестів має тривати лічені секунди без оверхеду на мережеву комунікацію з базою даних.

---

## 2. Розглянуті альтернативи (Alternatives Considered)

### Альтернатива 1: Використання виключно PostgreSQL для всіх середовищ
- *Переваги:* 100% ідентичність dev- та prod-оточень, відсутність розходжень у SQL-діалектах.
- *Недоліки:* Вимагає обов'язкової наявності встановленого Docker-демона або локальної СУБД PostgreSQL на машині розробника; ускладнює запуск на малопотужних хостах; уповільнює ізольований запуск швидких юніт-тестів.

### Альтернатива 2: Використання виключно SQLite для всіх середовищ
- *Переваги:* Максимальна простота, компактність (один файл бази даних), нульові витрати на інфраструктуру.
- *Недоліки:* Блокування всієї бази даних на запис (file-level lock), низька пропускна здатність при паралельних запитах користувачів у веб-середовищі, обмежена підтримка типів даних та аналітичних функцій.

### Альтернатива 3: Гібридний підхід через шар абстракції SQLAlchemy 2.0 ORM (Обрано)
- *Переваги:* Розробники та тести використовують файлову або in-memory SQLite за замовчуванням (zero-configuration start); у контейнерах Docker Compose та на Production сервіс перемикається на повнофункціональну PostgreSQL зміною одного рядка `DATABASE_URL`.
- *Недоліки:* Необхідність уникати специфічних вендор-діалектних фіч у моделях та відстежувати сумісність міграцій.

---

## 3. Прийняте рішення (Decision)

Ухвалити **Альтернативу 3**: реалізувати гібридну стратегію збереження даних за допомогою ORM **SQLAlchemy 2.0**:
- За замовчуванням у змінній `DATABASE_URL` встановлюється `sqlite:///./runtracker.db`.
- У виробничому середовищі (Production/Compose) передається DSN підключення до `postgresql+psycopg2://...`.
- Моделі описуються за уніфікованим декларативним стандартом SQLAlchemy без прив'язки до вендор-специфічних типів (наприклад, JSONB або ENUM).

---

## 4. Наслідки (Consequences)

### Позитивні наслідки:
- **Zero-config Onboarding:** Новий розробник запускає систему командою `python seed.py && uvicorn app.main:app` за 1 хвилину.
- **Швидкість CI-тестів:** 57+ тестів виконуються за менш ніж 3 секунди на локальній SQLite базі.
- **Гнучкість інфраструктури:** Просте горизонтальне розгортання в Docker/Kubernetes із зовнішнім керованим кластером PostgreSQL.

### Негативні наслідки та ризики:
- Ризик різної поведінки при роботі з типами дат (`DateTime` у SQLite зберігається як текст).
- Необхідність перевірки складних запитів як на SQLite, так і на PostgreSQL перед релізом у продакшен.
- Заборона використання функцій, специфічних для однієї СУБД (наприклад, PostgreSQL `RETURNING` у сирому SQL).
