## Завдання 2. Кастомний Quality Gate (3 бали)

**Quality Gates → Create** → назва `Custom-Gate-Lab1` → **Add condition** ×4 →
**Projects → Select** → прив'яжіть `runtracker`.

| # | Категорія | Умова в Sonar | Поріг |
|---|---|---|---|
| 1 | On New Code | Bugs | **= 0** (is greater than 0 → fail) |
| 2 | On New Code | Security Hotspots Reviewed | **= 100%** (is less than 100%) |
| 3 | On Overall Code | Duplicated Lines (%) | **≤ 3.0%** |
| 4 | On Overall Code | Cognitive Complexity | **≤ (baseline + 15%)** — підставте своє число |

> **Важливо про критерій 4.** У Quality Gate метрика `Cognitive Complexity` рахується
> сумарно по проєкту, тому поріг береться від Baseline із запасом (наприклад, baseline 95 →
> поріг 110). А обмеження **на один метод (≤ 15)** задається не в Gate, а в
> **Quality Profiles → правило `python:S3776` "Cognitive Complexity of functions should not be
> too high" → Threshold = 15**. На захисті це варто проговорити: gate контролює систему
> загалом, правило профілю — окремий метод. Якщо у вашій версії Sonar метрики
> `Cognitive Complexity` немає серед умов, замініть критерій 4 на
> **Maintainability Rating on Overall Code = A** або **Technical Debt Ratio ≤ 5%**
> і поясніть це в звіті.

### Архітектурне обґрунтування (готові абзаци для звіту)

**1. New Bugs = 0 (Zero Bug Policy на новому коді).**
RunTracker оперує даними, на підставі яких бігун планує навантаження: помилка в розрахунку
темпу, пульсової зони чи обсягу плану транслюється безпосередньо в ризик перетренованості
або травми. Дефекти в шарі `services` не мають візуального прояву в інтерфейсі — вони просто
повертають правдоподібне, але хибне число. Тому нові баги блокуються на рівні Pull Request:
вартість їх виправлення на етапі код-рев'ю на порядок нижча, ніж після релізу.

**2. New Security Hotspots Reviewed = 100%.**
Застосунок зберігає персональні дані (вік, пульс спокою, історія травм) — це чутлива
інформація про здоров'я. Hotspot не є доведеною вразливістю, тому автоматично його
відхилити не можна, але й пропускати без огляду не можна теж: саме через неперевірені
місця (рядки підключення до БД, робота з токенами, хешування) виникає більшість витоків.
Поріг 100% робить ручний аудит безпеки обов'язковою частиною процесу, а не доброю волею
розробника.

**3. Duplicated Lines % ≤ 3% (Overall Code).**
Бізнес-логіка проєкту сконцентрована в сервісах (`pace`, `gear`, `plans`, `analytics`),
і формули в них використовуються з кількох маршрутів одночасно. Копіювання такого коду
означає, що зміна формули (наприклад, ліміту пробігу кросівок) доведеться вносити в кількох
місцях, і одне з них неминуче забудуть — класична причина розходження поведінки API та
інтерфейсу. Поріг 3% встановлено з невеликим запасом до фактичного Baseline і відповідає
принципу DRY: дозволяє дрібні технічні збіги (схожі сигнатури, boilerplate), але блокує
копіювання логічних блоків.

**4. Cognitive Complexity (≤ 15 на метод / сумарний поріг на проєкт).**
Проєкт розвиватиметься саме в генераторі планів — додаватимуться нові дистанції, фази
підготовки, типи тренувань. Метод із когнітивною складністю понад 15 неможливо безпечно
змінити без повного перечитування: розробник не утримує всі гілки в робочій пам'яті, тому
кожна правка дає високу ймовірність регресії. Обмеження складності — це прямий контроль
вартості супроводу: воно змушує декомпозувати логіку в момент написання, а не через рік.

**Скріншоти для звіту:** вікно Quality Gate з усіма 4 умовами + Overview проєкту зі статусом
**PASS** (зелений).

## Завдання 4. Зниження Cognitive Complexity (2.5 бали)

### Дві проблемні ділянки (знайдіть їх у Sonar: Issues → Rule `python:S3776`)

| Метод | Файл | Проблема |
|---|---|---|
| `generate_training_plan()` | `backend/app/services/plans.py` | 5 рівнів вкладеності: `if runner` → `if weeks > 0` → `for week` → `for session` → `if/elif` |
| `check_equipment_status()` | `backend/app/services/gear.py` | `if/else` на 4 рівні + ланцюг `if/elif/elif/else` для порогів зносу |

У Sonar відкрийте кожен issue — він показує **точне значення складності** та **час на
виправлення** (це і є Technical Debt для ділянки, розрахований за моделлю SQALE:
аналізатор множить кількість «зайвих» пунктів складності на нормативну вартість правки).
Випишіть ці числа у звіт **до** рефакторингу.

### Рефакторинг

Готові версії «ПІСЛЯ» вже лежать у репозиторії й проходять ті самі 30 тестів без жодної
зміни в тестах — це доказ, що поведінка збереглася:

```bash

cp docs/refactoring/gear_refactored.py  backend/app/services/gear.py

git commit -am "refactor: reduce cognitive complexity with guard clauses and extract method"

```

**Не копіюйте наосліп** — перед захистом прочитайте обидва файли: викладач питатиме, які
саме техніки застосовані і чому вони знижують метрику.

### Що саме змінилося (для розділу «Code Review» у звіті)

**`generate_training_plan()`:**

- **Guard Clauses** — замість `if runner is not None:` з тілом на 40 рядків тепер
  `if not runner or weeks <= 0: return []` на початку. Зник перший рівень вкладеності,
  а з ним — обов'язок читача пам'ятати, «в якій гілці ми зараз перебуваємо».
- **Extract Method** — логіка розбита на `sessions_per_week()` (скільки тренувань на
  тиждень), `week_shape()` (фаза тижня та довжина довгого бігу), `session_profile()`
  (тип тренування і його частка), `build_workout()` (складання одного дня). Кожна функція
  має одну відповідальність і зрозумілу назву.
- **Replace Nested Conditional with Lookup Table** — ланцюг `if beginner / elif
  intermediate / else` замінено словником `SESSIONS_BY_LEVEL`; додати новий рівень
  підготовки тепер означає додати рядок у словник, а не гілку в умову.
- **Магічні числа → іменовані константи** (`TAPER_FACTOR`, `RECOVERY_FACTOR`,
  `WEEKLY_PROGRESSION_KM`): код став самодокументованим.

**`check_equipment_status()`:**

- **Guard Clauses** для двох вироджених випадків (`shoe is None`, списана пара) — обидва
  повертають результат одразу, `else`-гілка на весь метод зникла.
- **Extract Method**: `mileage_limit()` (розрахунок ліміту з поправками на травми, обсяг
  і рівень) та `wear_status()` (статус за часткою зносу).
- **Таблиця порогів** `WEAR_THRESHOLDS` замість `if/elif/elif/else`: бізнес-правила зносу
  тепер лежать у даних, а не в керуючих конструкціях, і редагуються без ризику зачепити логіку.

## Технічний висновок (каркас, доповніть своїми числами)

**Cognitive vs Cyclomatic Complexity.** Цикломатична складність рахує кількість незалежних
шляхів виконання і відповідає на інженерне запитання «скільки тест-кейсів потрібно, щоб
покрити всі гілки». Вона байдужа до форми коду: плаский `switch` із 10 гілками та чотири
вкладені `if` усередині циклу можуть мати однакову цикломатичну складність, хоча читаються
абсолютно по-різному. Когнітивна складність вимірює інше — зусилля людини на розуміння коду.
Вона не нараховує штраф за лінійні структури (`switch`, послідовність `elif`), зате додає
зростаючий штраф за кожен рівень вкладеності та за розриви лінійного читання (`break`,
`continue`, рекурсія, складені логічні вирази). Саме тому в нашому випадку метод
`generate_training_plan` мав прийнятну цикломатичну складність, але критичну когнітивну:
проблемою була не кількість гілок, а глибина драбинки. Для контролю супроводжуваності
когнітивна складність інформативніша, для планування тестового покриття — цикломатична;
на практиці їх використовують разом.

**Про доцільність автоматичного контролю боргу на комерційних проєктах.** Quality Gate
переводить якість із категорії домовленостей у категорію умов збирання: поки борг не
виміряний і не заблокований технічно, він накопичується непомітно — кожна окрема правка
здається дешевою. Автоматичний контроль дає три ефекти: борг фіксується в момент появи,
а не на етапі, коли команда вже «не має часу»; критерії однакові для всіх розробників і не
залежать від авторитету автора PR; вартість виправлення вимірюється в годинах і стає
аргументом у розмові з менеджментом. Обмеження теж очевидні: надто жорсткі пороги на
легасі-проєкті блокують роботу, тому розумною є саме та стратегія, яку ми застосували —
суворі вимоги до нового коду (New Code) і стримувальні ліміти на код історичний
(Overall Code), щоб система не деградувала далі.
